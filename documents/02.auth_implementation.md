# Task: Integrate Existing Backend Authentication with Auth.js (NextAuth.js v5)

Implement a complete, production-oriented authentication integration using Auth.js (NextAuth.js v5) in the existing Next.js ecommerce frontend.

**Important: Focus ONLY on authentication functionality. Do not work on UI, styling, login pages, registration pages, or form components.**

## 1. Understand the Existing Backend First

The backend is available in the `dress-ecomm-backend` repository.

Before implementing anything:

1. Inspect the backend repository and understand its authentication architecture.
2. Find the existing login API.
3. Find the registration API.
4. Find the refresh token API.
5. Find the Google social login API.
6. Find the logout API.
7. Understand the request payloads, response structures, status codes, token formats, and cookie handling.
8. Inspect the existing frontend project structure and dependencies.
9. Identify the correct integration points.

Do not assume API endpoints, request fields, response structures, or token formats.

Use the actual backend implementation as the source of truth.

Do not modify the backend unless explicitly required. If an incompatibility exists, explain it before proposing changes.

## 2. Auth.js Configuration

Use Auth.js v5 with the existing Next.js application.

Requirements:

- Configure Auth.js using the recommended Next.js App Router integration.
- Keep the authentication configuration modular.
- Export and reuse `auth`, `handlers`, `signIn`, and `signOut` where appropriate.
- Configure the authentication route handler correctly.
- Use environment variables for all secrets and backend URLs.
- Never hardcode credentials.
- Follow the existing project folder structure.
- Avoid unnecessary dependencies.

## 3. Credentials Authentication

Integrate the existing backend login API with the Auth.js Credentials Provider.

Expected flow:

1. Receive login credentials on the server.
2. Validate the incoming data.
3. Call the existing backend login API from the server.
4. Validate the backend response.
5. Handle authentication failures securely.
6. Establish the Auth.js session.
7. Store sensitive backend authentication credentials exclusively in server-controlled storage.

Important:

- Never call the backend login API directly from browser-side code.
- Never expose backend access tokens or refresh tokens to client components.
- Never trust user information supplied by the browser.
- Do not store passwords after authentication.
- Do not log credentials or tokens.

## 4. Registration Integration

Integrate the existing backend registration API.

Requirements:

- Implement the registration functionality through a server-side integration.
- Validate registration data before submitting it.
- Use the existing backend validation rules and response structure.
- Handle duplicate email addresses and other validation errors.
- Never automatically authenticate a newly registered user unless the existing application requirements explicitly support it.
- Never expose sensitive backend responses.

Do not build registration UI.

## 5. Google Social Login

Integrate Google authentication with the existing backend social login implementation.

First, inspect how the backend currently handles Google authentication.

Determine whether it expects:

- Google ID token.
- Authorization code.
- Another supported OAuth credential.

Implement the correct flow based on the backend contract.

Security requirements:

- Use Auth.js Google Provider.
- Validate OAuth state and PKCE where applicable.
- Validate the Google identity and token according to the selected flow.
- Never trust an email address supplied directly by the browser.
- Do not automatically link accounts based only on an unverified email.
- Prevent account takeover through unsafe account linking.
- Do not expose Google access tokens or backend tokens to client components.
- Handle cancelled OAuth flows and failed authentication safely.

Avoid implementing a second independent Google authentication system if the backend already provides the required integration.

## 6. Server-Side Session Management (CRITICAL)

This is the most important requirement.

**Session access must be server-side only.**

Use Auth.js server-side `auth()` to retrieve the authenticated session.

Examples of expected usage:

- Server Components.
- Server Actions.
- Route Handlers.
- Server-side authorization checks.

Requirements:

- Use the server-side `auth()` function.
- Do not expose backend access tokens or refresh tokens through the session object.
- Do not expose sensitive authentication information through the JWT callback or session callback.
- Do not implement client-side token management.
- Do not use localStorage or sessionStorage for authentication credentials.
- Do not create unnecessary client-side session providers.
- Do not use `useSession()` or `SessionProvider` as the primary authentication mechanism.

The session should contain only the minimum safe user information required by the application.

For example:

- User ID.
- Name.
- Email.
- Role, if required for displaying information.

All sensitive authentication credentials must remain server-side.

## 7. Token Storage Architecture

Inspect the backend token implementation before deciding how to store credentials.

Prefer a secure server-side persistence architecture:

- Use Auth.js database sessions with a compatible adapter if appropriate.
- Keep backend access and refresh tokens in server-only storage.
- Never serialize backend credentials into client-visible session objects.
- Ensure session identifiers are unpredictable.
- Use appropriate database access controls.
- Never expose token records through public API endpoints.

If the backend already manages refresh tokens through secure HttpOnly cookies, determine whether that mechanism can be safely integrated without duplicating token management.

Do not blindly introduce a second refresh-token system.

Document the selected architecture and explain why it is secure.

## 8. Access Token Refresh

Integrate the existing backend refresh API.

Requirements:

1. Detect expired or near-expiry access tokens on the server.
2. Call the existing refresh endpoint.
3. Validate the refresh response.
4. Update the stored access token.
5. Rotate and persist the refresh token if the backend supports rotation.
6. Retry the original authenticated backend request only when appropriate.
7. Handle invalid, expired, revoked, or reused refresh tokens.
8. Invalidate the session when authentication can no longer be recovered.

Important security requirements:

- Never refresh tokens from client-side components.
- Never expose refresh tokens through API responses intended for the browser.
- Prevent concurrent refresh operations from using the same rotating refresh token.
- Handle refresh-token rotation atomically where possible.
- Avoid infinite refresh loops.
- Do not blindly retry failed requests.
- Ensure multiple simultaneous requests cannot corrupt token state.

Use a centralized server-side refresh mechanism rather than duplicating refresh logic across API functions.

## 9. Logout

Integrate the existing backend logout API.

Expected behavior:

1. Identify the authenticated server-side session.
2. Revoke or invalidate backend authentication credentials using the existing logout API.
3. Clear the server-side authentication session.
4. Expire the relevant authentication cookies.
5. Prevent further access using the invalidated session.

Handle logout failures carefully. Local session cleanup must still occur even if the backend logout request fails.

Never expose refresh tokens to the browser to perform logout.

## 10. Route Protection and Authorization

Implement server-side authentication and authorization helpers.

Requirements:

- Create reusable server-side authentication utilities.
- Provide a way to retrieve the current authenticated user.
- Provide a way to require authentication.
- Provide a way to require specific roles or permissions.
- Reject unauthorized requests on the server.
- Protect admin operations independently of frontend visibility.
- Never rely on middleware or frontend redirects as the only security boundary.
- Validate authorization for every sensitive operation.

Use the existing user roles and permissions from the backend.

Do not invent new roles.

## 11. Security Requirements

Apply the following security practices:

- HttpOnly authentication cookies.
- Secure cookies in production.
- Appropriate SameSite configuration.
- CSRF protection for state-changing operations.
- OAuth state and PKCE validation where applicable.
- Strict server-side input validation.
- Safe error handling.
- No sensitive information in logs.
- No tokens in URLs.
- No credentials in browser storage.
- No sensitive information in client-side session responses.
- Prevent open redirects.
- Protect against session fixation.
- Use session expiration and appropriate idle timeout policies.
- Never trust client-provided roles or user IDs for authorization.
- Keep authentication secrets in environment variables.

Follow Auth.js security defaults wherever possible. Do not disable built-in protections to make integration easier.
